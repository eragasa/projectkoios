Its mirrored paths support selective review; they do not make every artifact a
runtime component or transfer target. This document records the current state

## Current disposition

### Adapter taxonomy

Adapter, Binding, and Integration remain nominal architecture vocabulary. The
unused behaviorless runtime base is not an extraction target, and no runtime
owner exists for it. A runtime nominal base requires a real consumer, a shared
invariant, and an explicit owner. The current taxonomy is documented in the
[adapter architecture](architecture.adapters.md).

### Material charge model

`materials/charge.py` remains incubated in Frankenstein. It has no destination
namespace or transfer owner until a real consumer and an explicit owner review
establish its boundary. Incubation does not authorize namespace redesign.

### Probability and validation behavior

Reviewed `projectkoios-optimization` commit
`ce231c4de03c561b63a91386f02d177b4f26d037`, tree
`1259816ffddaf35c63c97684a60f73b52435ab75`, supersedes the Frankenstein NumPy
probability, binding, and generic validator semantics. Project Koios promises
no NumPy `RandomState` API or sequence compatibility and does not copy that
legacy behavior without a real consumer and a separately reviewed boundary.

### Non-transfer targets

The following are not transfer targets:

- the empty `projectkoios_snakes` marker;
- independent tutorials and mockups; and
- the generic behaviorless validation base.

These artifacts do not route into `projectkoios-workflow` and do not establish
workflow or CPN capability.

### Provenance-only material

Historical engine metadata and catalogs, donor license and source declarations,
bounded documentation and manifests, and the 481 source-derived artifacts
remain non-executed reconstruction and provenance evidence in Frankenstein
only. They are not:

- simulation or application runtime;
- maintained examples;
- numerical verification; or
- scientific validation.

`projectkoios-simulations` owns maintained neutral simulation abstractions and
provider integrations. `projectkoios-applications` owns accepted application
composition. Provenance-only material is not adopted by either owner merely
because it describes engines, providers, or reconstructed application sources.

## Transfer and authority limits

A mirrored overlay path is a review aid, not an automatic migration rule. A
future transfer requires a concrete consumer, an explicit owner, a reviewed
contract, and exact source, license, and rightsholder checks for every copied
item.

The current disposition authorizes no:

- deletion or mutation of Frankenstein evidence;
- extraction or copying;
- relicensing;
- runtime execution;
- repository or remote creation;
- merge, push, or publication; or
- representation of reconstruction evidence as numerical verification or
  scientific validation.

An item that is not transferred has no assigned destination. That status does
not authorize deletion of the source evidence.
